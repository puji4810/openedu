# StudyOS applies a day plan as events only

An Intervention Queue names the capability least supported by evidence and a Schedule phase names what the week is for, but neither answers "what do I do today", so in practice every Schedule carried phases and an empty `events` list and the day-level calendar had nothing to render. StudyOS now projects the queue onto dated events inside a study window derived from the Learner's own timestamped attempts, carries that projection on the Plan Proposal, and applies it through `plan_proposal.apply`.

Applying stays the third act of [0003](./0003-study-os-keeps-proposals-separate-from-schedules.md) rather than folding into acceptance, but it is narrowed until it is safe to be one call: it requires an accepted proposal, writes only the events that proposal already contains, refuses when the covering phase has changed since derivation, and asserts structurally that nothing but `events` differs before writing. Phases and range still require an explicit `schedule.validate` and `schedule.save`, so accepting a day can never rewrite the long-term plan, and cron remains blocked from applying just as it is from deciding.

Deriving the day is idempotent per date rather than per fingerprint. A plan is anchored to the current time so it never proposes a session that has already passed, which means re-deriving in the evening what was derived in the morning legitimately produces different events; keying reuse on "a proposed plan already exists for this date" is what stops the Learner accumulating a new proposal every time they open the app, and a date already accepted or rejected is not proposed again.
